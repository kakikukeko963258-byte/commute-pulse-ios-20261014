# 位置・時刻表の推定

`CommuteCore` は Foundation のみを使用する Swift package です。通常の Core Location / Core Motion 入力も、明示されたシミュレーションも `CommuteEngine.ingest` に同じ `TravelObservation` を渡します。位置、加速度由来の MotionEvidence、駅履歴はメモリ内で扱い、外部へ送信しません。共有する `ProgressSnapshot` に生の位置や加速度は含みません。

路線は同梱した線路形状の各折れ線へ投影し、線路からの距離、前回との差、速度、進行方向、駅の順序、運行日と予定時刻を組み合わせます。`automotive` を電車判定の根拠に加算しません。並走する道路や地下での誤差を完全には排除できないため、乗車表示も推定です。信頼度 high は複数駅の一致などを意味し、鉄道事業者が列車位置を確認したことを意味しません。

出発駅の入力は必須ではありません。恵比寿など途中駅の最初の有効観測から路線・方向・候補を評価します。新しい駅に到着した観測は候補を再評価し、発表された到着時刻がない場合の発車時刻を、明示された推定値として利用します。観測と予定時刻の差が180秒以内なら、その観測を元に後続の予測区間を補正します。この補正は端末の推定であり、公式の遅延情報には変換しません。

候補のスコアは時刻表との一致を順位づけする値であり、乗車列車の確率ではありません。上位差が小さいときは列車を確定しません。GPS精度が50mより悪いときは必要なスコア差を増やし、最近の駅履歴が2駅未満ならさらに保守的に扱います。精度が駅近接判定の半径以上（標準110m、180mの観測を含む）では、複数候補のどれかを選択せず確度を低くします。全候補が同じ区間と30秒以内の時刻に一致するときのみ共通するバーを出します。異なる区間ならタイマーは保留し、候補数と不確実性を表示します。山手線の大崎をまたぐサービスに継続運転の確認がない場合、同じ列車として大崎を越えた予測を行いません。

GPSが欠落した後も、最後の整合した候補と時刻区間を元に進捗を予測します。最初から位置が不明な場合に乗車路線を勝手に作ることはできません。最後の有効位置から150秒で確度を低くし、45分で未確認の進捗を保留します。予定での終点到着は到着推定として示し、実位置の到着確認とは区別します。

Widget/Live Activity の区間バーは `segmentStart...segmentEnd` と `progressFromStationID/progressToStationID` を受け取り、システムの時間連動描画を使います。急行の区間は通過駅をまたぎます。`projectedTimeline` は将来の停車境界を出すのでWidgetの駅名更新も事前に計画できます。ActivityKitのヘッダー更新や候補再評価は位置取得・アプリ実行の機会が必要であり、バックグラウンドの毎秒実行を保証しません。

時刻は `Asia/Tokyo` の営業日と0時からの分数です。1440分以上の出発は翌日の日付へ変換され、平日・土休日・同梱祝日・限定運転日・運休指定日と適用期間を評価します。祝日データの `coveredFrom...coveredTo` の範囲外は平日と決めず、列車に明示された限定運行日がある場合だけ照合を許可します。祝日や時刻表の適用期間が過ぎたときはデータの差し替えが必要です。現状の分単位データは秒単位の駅停車を表しません。終着駅で発車が公表されていない場合は `departurePublished=false` の到着時刻を終端時刻として扱い、発車があるとは主張しません。

テスト用の人工時刻表は `Tests/CommuteCoreTests` にだけあります。発駅未検出、途中駅復帰、逆方向、日付またぎ・祝日、急行、GPS欠落、同順位候補、精度8mと180mでの候補選択の違い、大崎継続未確認、曲線形状、共有データの時刻区間保存を検証する XCTest ソースを用意しています。ビルドとテストは GitHub Actions の macOS runner で実行し、結果は各 run のテストレポートで確認します。
